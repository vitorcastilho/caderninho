## O Que Deu Certo

### 1. Blueprint Clean Architecture (Story 2.1)
A Story 2.1 definiu o padrão completo Server Action → Use Case → Repository com Result Pattern, DI via factory, auditoria e TDD. Esse blueprint sustentou todas as 6 stories seguintes com complexidade crescente — de 1 entidade (2.1) a 3 entidades com merge (2.4) a wizard multi-step reutilizando todas as actions (2.6).

### 2. TDD Consistente
250 testes na 2.1, crescimento orgânico até 637 no final do épico. Zero regressão séria ao longo do caminho. O padrão de testes co-localizados com mocks de Drizzle client funcionou bem.

### 3. Code Review Amadureceu
O processo de review evoluiu significativamente:
- **Foco em bugs reais:** HIGHs e MEDIUMs são bugs concretos, LOWs vão pro backlog
- **Convergência rápida:** R1 encontra, R2 valida fixes. Máximo 2 rounds
- **R2 não inventa findings novos:** R2 valida o que R1 pediu, não faz segunda varredura
- Tendência clara: de 7 findings com CRITICAL na 2.1 para 0 HIGHs na 2.4

### 4. Evolução do Padrão de DI
- 2.1: Use cases importavam direto de `infrastructure/` (review pegou como HIGH)
- 2.2: Factory com deps injetadas
- 2.4: Factory compartilhada pra 3 repositórios no mesmo domínio
- Padrão maduro e replicável

### 5. Zero Incidentes em Produção
7 stories, 637 testes, 14 reviews. Nenhum incidente.

### 6. Protótipos como Referência (Quando Consultados)
O sistema de protótipos HTML funcionou bem como referência visual canônica — o problema não foi a qualidade dos protótipos, mas a falta de consulta sistemática.

## O Que Não Deu Certo

### 1. Design System Sistematicamente Ignorado (CRÍTICO)
O problema mais grave do épico. Apesar de existirem protótipos e página `/design-system`:
- Dev não consultava protótipos nem DS sem ser forçado
- Componentes eram inventados fora do padrão quando não existiam no DS
- A Story 2.7 (auditoria visual) foi reativa — corrigiu desvios em vez de preveni-los
- Cada story nova acumulava dívida visual

**Impacto:** Vitorcastilho precisou parar o desenvolvimento para criar a página `/design-system` com Sally. Mesmo assim, inconsistências continuaram.

### 2. Protótipos Inconsistentes Entre Si (CRÍTICO)
- Cada protótipo tem sidebar diferente — nenhum reflete a implementação real
- Valores monetários: alguns mostram `R$ 3.000`, outros `R$ 3.000,00`
- Percentuais: alguns mostram `25%`, outros `25,03%`
- Mobile e desktop misturados: tem telas só mobile, só desktop, e casos onde parecem sistemas diferentes
- Tokens visuais (botões, espaçamentos, cores) divergem entre protótipos de épocas diferentes

**Impacto:** Três fontes de verdade conflitantes (protótipos, DS, código). Dev não sabe qual seguir.

### 3. Drizzle-kit Migrate Travando (Recorrente)
Apareceu nas Stories 2.1, 2.4 e 2.6. O comando simplesmente trava sem erro. Solução: aplicar migration manualmente via `psql`. Nunca foi documentado como workaround formal — cada vez o dev perdia tempo investigando.

### 4. Contrato Repository/Use-Case Quebrado (Story 2.6)
Na Story 2.6, o repository retornava `boolean` mas use cases checavam `null`/`undefined`. O erro `ORGANIZATION_NOT_FOUND` era dead code. Deveria ter sido pego pelo TDD.

## Decisões de Produto Tomadas

### 1. Override de Método de Pagamento por Subcategoria (Opção B)
**Contexto:** Story 2.5 implementou método de pagamento padrão por categoria, mas na prática o padrão faz mais sentido por subcategoria (ex: Moradia → Aluguel é débito, Internet é cartão).
**Decisão:** Manter na categoria como fallback + adicionar override na subcategoria. Hierarquia: subcategoria override → categoria fallback → nenhum.
**Origem:** `_bmad-output/itens-para-discussao-pm.md` item 1.

### 2. Débito = Conta Bancária (Opção B)
**Contexto:** Schema de cartões só suporta crédito. Cartão de débito não tem como ser cadastrado.
**Decisão:** Não criar entidade separada. Débito é inerente à conta bancária. O método de pagamento "débito" aponta para a conta. Ajustar labels e copy.
**Origem:** `_bmad-output/itens-para-discussao-pm.md` item PM-2.

### 3. BankLogo — Componente de Logo de Bancos
**Contexto:** Ícone de conta mostra iniciais genéricas ("In", "It"), visualmente pobre.
**Decisão:** Criar componente `BankLogo` com cor institucional e sigla estilizada (15-20 bancos BR). Fallback para iniciais genéricas.
**Origem:** `_bmad-output/itens-para-discussao-pm.md` item PM-1.

## Acordo de Time: 4 Barreiras de Design System

1. **Story:** Task numerada obrigatória "Consultar DS e protótipos relevantes" com referências específicas

3. **Code Review:** Critério explícito — tokens de cor, border-radius, espaçamentos, componentes do DS vs HTML nativo
4. **Componente novo:** Dev não inventa. Pede → Sally prototipa → implementa no DS → dev importa
